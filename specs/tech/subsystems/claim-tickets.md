# Claim tickets: technical design

Status: proposed design, 2026-11-16. No contracts or service are implemented by this document. Product: [claim ticket](/specs/product/claim-ticket.md). Implementation is demand-gated by that page's “When to build” section.

## Decision and boundary

Use a ticket-aware assurance contract, with a fresh transit signing address as its initial recipient authority. Redemption permanently binds a destination inside that project. Funds never leave the project merely because a ticket is redeemed. Do not deploy a second escrow or use `BeneficiaryIdentity` / `BeneficiaryRegistry`. The transit address is a signing capability, not a payable wallet Bob imports.

This extends [per-project proceeds](/specs/decisions/0015-per-project-beneficiary-proceeds.md). A direct EOA recipient cannot rotate today: `IdentityHeldProceeds.fixedPayout` is immutable, `_payout()` is not virtual, and `claim()` transfers to that payout. A forwarding contract would receive tokens and introduce another stuck-balance surface. Instead refactor the authorization hook narrowly, retaining the existing surplus/reimbursement accounting, and add a ticket-specific project variant. Existing fixed and public-identity projects retain their authorization rules.

## Creation and state

The browser generates a cryptographically random secp256k1 transit key locally, once per project, and derives its address. A dedicated factory entry point atomically creates and records the ticket project, transit address, token, normal threshold/deadline, and work condition. There is no administrator, cancellation window, expiry of the secret independent of project rules, or issuer recovery. The creator can still redeem if they retained the code; disclose this before creation and on delivery.

On-chain ticket state is `transitAddress`, `destination` (initially zero), and `redeemed` (initially false). The project's address and chain identify the ticket; no name, mailbox, or public identity is stored. Factory events establish that a project is a ticket project; metadata alone cannot assert this. The factory records the transit address and rejects a duplicate, so a derived address looks up at most one ticket project. Deploy with the ordinary `new` or clone path. Do not add CREATE2 or a predict-before-deploy API in v1. Deterministic deployment is deferred until a real case needs the claim code to name the project address before creation confirms.

Keep the transit key in memory through submission. Build and offer the claim code only after the creation receipt confirms, then verify the factory event, deployed address, transit address, and creation parameters before delivery. Require the issuer to copy or download that code and acknowledge it before the UI offers funding. No automatic local-storage backup. Nothing may be sent to a transit address, and the project must not be fundable, until that acknowledgement. If creation reverts, discard that key and generate a new one for another attempt. On a timeout or ambiguous status, query the original transaction hash; do not silently generate another key or create another project until that attempt is known to have failed. If the browser closes after submission but before the code is exported, a confirmed project can be left unredeemable until its normal deadline refunds. That loss is accepted in v1; funding must still be blocked so it cannot strand a contribution.

## Redemption protocol

`redeem(destination, transitSignature, destinationSignature, deadline)` is permissionless to submit. Both signatures authorize the same typed action, domain-separated by chain ID, project address, protocol version, action `RedeemClaimTicket`, nonce zero, destination and deadline. Require an unexpired deadline, a nonzero destination distinct from the transit address and project, an unused ticket, and a valid transit ECDSA signature. Require destination consent using ECDSA or ERC-1271 against this exact action. This works with a deployed passkey smart account; an undeployed account must first be deployed by its normal onboarding flow. Counterfactual signature support is outside v1.

Consume the ticket and set the destination atomically before external calls; use reentrancy protection around signature validation. There is no arbitrary call target, token allowance, generic execution, or caller-selected payout in redemption. The transit key cannot claim proceeds, accept work, or refuse the project before redemption. After redemption only the bound destination has those rights. Concurrent redemptions serialize: first valid inclusion wins, all later attempts revert. Copying a pending transaction can only bind the signed destination. A retained or stolen code can sign a competing destination; this is intrinsic bearer risk, not relay authority. Reject new redemption after failure, refusal, or closure of the successful-proceeds claim window; a failed transaction does not consume the ticket.

Redemption binds authority; it does not assert that work was accepted or funds claimed. Bob reviews and separately accepts or vetoes the work proposal, and later claims or refuses proceeds. The first version has no destination rotation: Bob chooses a durable account with its own recovery mechanism. A spent code never regains authority.

## Fit with existing work and proceeds rules

`ProjectFactory._wireUpAndFinalize` currently marks another-wallet projects third-party, wraps their condition in `WorkFundingCondition`, and scopes work IDs to `walletWorkBeneficiary(recipient)`. A ticket cannot just be passed to the existing recipient field: nobody could accept through the future destination. Add a ticket-aware work-authority resolver that returns zero before redemption and the bound destination afterward. Route factory `acceptWorkProject` / `vetoWorkProject` through that resolver without allowing the issuer or transit signer to pre-accept. Keep the normal third-party acceptance and seven-day veto period; Bob must redeem and accept sufficiently before the project deadline. Threshold reached alone is not success. Do not bypass delegation checks or shorten their waiting periods.

Work identity stays scoped to the immutable transit address for the life of this attempt, even after redemption. Redemption neither releases nor re-registers work reservations. The UI must not promise that this prevents the same real-world work from appearing under a different ticket or Bob's wallet; identity conventions already have that limit.

| Situation | Result |
|---|---|
| Before success | Redemption only binds Bob's account. Normal acceptance/veto, contribution and deadline rules continue. |
| Successful and still unclaimed | Bound account calls existing `claim()`; transfer uses only `withdrawableRecipientBalance()`. Redemption itself starts no new clock. |
| Refusal before success | Bound account calls existing `refuse()`; ordinary contributor refunds open. |
| Refusal after success | Contributor surplus return opens immediately; reimbursement reserves remain reserved. |
| Never redeemed / never accepted | Work proposal expires at deadline and contributors refund normally. |
| Successful but unclaimed | Anyone can `noteSuccess()`; at 90 days contributors reclaim surplus under existing share accounting. No fallback payee. |
| Claim and reclaim compete at boundary | Existing timestamp rule applies: claim requires time strictly before closure; reclaim opens at closure. |

The successful-before-redemption row is defensive support for future conditions; v1 third-party work cannot succeed before Bob redeems and accepts. Future proceeds and retroactive donations use the bound account and existing reserve rules; the transit key cannot sweep them. Claiming remains separate from redemption and repeat claims follow existing project accounting. Never reset `succeededAt`, acceptance state, supply snapshots, or reserves on redemption.

## Relay and code handling

The Commonality platform API operator initially runs an optional gas-funded relay, with a dedicated bounded-balance transaction signer. Anyone may run another relay or submit directly. The browser sends only the signed redemption payload, never the code or key. Relay configuration allowlists chain and factory deployment, verifies factory provenance and current state, simulates the exact call, caps gas and request size, rate limits, and submits only `redeem` to that project. It cannot replace the destination or charge fees from proceeds. Sponsorship exhaustion returns a retryable error and a payload usable with another relay; it never redirects funds. Account deployment and subsequent project actions use existing wallet gas arrangements, separately from this redemption sponsorship.

Encode the code as `ct1:` plus base64url of a versioned binary payload containing chain ID, project address, 32-byte transit key and checksum. The project address is known only after creation confirms; it is a convenience and a cross-check, not something the code must carry before deployment. The checksum detects transcription errors, not tampering. Validate lengths/version/chain and derive the transit address locally, then compare it to authoritative project state before signing. If the pasted code has no usable project address, look the ticket up by that derived transit address. A duplicate or missing registration is a hard error. Never encode it as mnemonic words or label it a wallet key. Show “Anyone with this code can claim this project, including its creator.” The manually pasted code is the default; optional links carry it only in a URL fragment, remove the fragment immediately, and never load third-party analytics on the claim route. Do not log codes, signatures containing secrets, clipboard contents, or form values; do not put the secret in IPFS, query strings, events, relay requests or error telemetry. Clear transient key material after signing and on leaving the route, acknowledging browser memory cannot guarantee erasure.

## Implementation and acceptance gate

When the product trigger is real, implement contracts/factory and tests first, then SDK event folds and signing, relay, and creation/claim UI together. Register new events in the raw-event indexer configuration; compute state in SDK folds. Add deployed addresses and chain-scoped relay configuration through the existing deployment machinery. No migration of existing projects is implied.

Required tests: duplicate transit-address registration; wrong chain/project/action/destination/deadline signatures; zero/self/transit destinations; EOA and ERC-1271 consent; callback reentrancy; duplicate and concurrent redemptions; copied pending transactions; stolen-code competing signatures; relay provenance, budget and target restrictions; ambiguous creation does not start a second project; pre-redemption acceptance/refusal/claim denial; post-redemption transit denial; unchanged work reservations and delegation waits; failed/unaccepted deadlines; success note and exact 90-day boundary; refusal before/after success; claims that preserve reimbursement reserves; subsequent donations; stale indexer state versus authoritative simulation. Browser acceptance must cover fresh-account deployment, code export only after confirmation, funding blocked until that export is acknowledged, reload and malformed codes, lookup by derived transit address, no secret telemetry, relay outage fallback, and visibly separate work acceptance and proceeds claim. Security review of these authorization/accounting changes precedes deployment.
